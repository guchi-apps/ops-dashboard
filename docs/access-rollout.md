# 共通アクセス設定の各アプリへの導入（#490）

StatusHubの共通アクセス設定（[access-control.md](./access-control.md)）を、ログイン許可を持つ自作アプリへ順に導入する。
**このリポジトリを含め、対象アプリのリポジトリはすべて公開されている。** ここにはアプリ名・状況・Issue/PRへのリンク・共通ルールだけを書き、
アプリ別の弱点や迂回できる経路の詳細は書かない（非公開の共有知識リポジトリ `guchi-apps/docs` に置く）。メール実値・トークンも書かない。

## 対象一覧と状況

状況は「未着手」→「導入中」→「移行済み」→「本番検証済み」の順に進める。**PRのマージだけで「本番検証済み」にしない**
（管理画面で「反映済み」になり、許可・取り消しが実機で効くことを確かめてから）。

| アプリ | 状況 | 導入Issue/PR |
| --- | --- | --- |
| StatusHub（status-hub） | 本番検証待ち（#489でマージ済み） | status-hub#489 |
| yoteiflow（**代表アプリ**） | 導入Issue起票済み | guchi-apps/yoteiflow#941 |
| morrow / dayspan / car-care / issue-deck / db-console / research-desk（work-relay） | 未着手 | 代表の結果を見て起票 |
| aide / myroom / signaly / clip-hive | 未着手 | 同上 |
| asset-manager / meisai-lab | 方針確認中 | 同上 |

- 代表は、構造が標準的で判定箇所が小さく、アーカイブされていない yoteiflow とした。先行導入と検証の結果を、残りのアプリの導入Issueに反映する
- アーカイブ済み・静的サイト・未実装のアプリは対象外
- 管理画面「アプリ」タブでは、導入が済んでいないアプリは「未連携」と表示される

## 導入の共通ルール

1. **先に管理画面「アプリ」タブでアプリと対応する権限を登録する**（起動時に自動で登録されるのは `status-hub` だけ。未登録のアプリへの `import` はエラーになる）。
2. **切替前に既存許可を移し、差分を確かめる。** 下の移行CLIで `import --dry-run` → `import` → `diff` を行い、欠落が0であることを確認する
3. **切替後は旧環境変数を判定に使わない。フォールバックにもしない。** 判定APIが使えないときに旧リストで通すと、StatusHubで取り消した利用者が通ってしまう。旧設定（1Password・環境変数・GitHub Secrets・同期マニフェスト）の整理は、移行検証と復旧確認の後に行う
4. **判定は契約どおり。** 結果は `ttlSeconds`（30秒）だけキャッシュし、取得できないときは直前の判定を `maxStaleSeconds`（5分）まで使う。超えたら拒否し、一度も判定できていない利用者は拒否する。許可は広げない
5. **アプリ単位で分ける。** アプリ別トークンは自アプリの判定だけを引ける。アプリ側の取り消しや失効で、ほかのアプリのセッションをまとめて失効させない
6. **ブラウザの申告を信じない。** アプリのサーバーが検証した `sub`・メール・`emailVerified` だけを判定APIへ送る
7. 5分以内ごとにハートビートを送り、管理画面で「反映済み」になることを確かめる
8. 本番反映の証拠（反映済みの表示、許可・取り消しの確認日）を各導入Issueに記録する

## 移行CLI（`scripts/access-migrate.mjs`）

本番サーバーで動く。Node標準のモジュールだけで、`ACCESS_DB_PATH`（未設定なら `./.data/access.sqlite`）のDBを直接読み書きする。
旧リストは**標準入力のパイプ**で渡す（シェルの履歴や環境変数に値を残さない）。**出力は件数だけで、メールの実値は出ない。**

```bash
# 1Passwordの値など、旧リストを出力するコマンド | ...
<旧リストを出力するコマンド> | node scripts/access-migrate.mjs import <appId> <権限> --dry-run   # 書かずに件数だけ確認
<旧リストを出力するコマンド> | node scripts/access-migrate.mjs import <appId> <権限>
<旧リストを出力するコマンド> | node scripts/access-migrate.mjs diff <appId>                      # 欠落があれば終了コード2
```

`import` の規則は管理画面の更新と同じ書き込み規則に合わせている。

- 権限はそのアプリが対応するもの（管理画面「アプリ」で登録した権限）だけ。未登録のアプリ・未対応の権限・空の入力はエラー
- 対象アプリの付与だけを足す。**ほかのアプリの付与や既存の権限は変えない**
- **StatusHubで取り消し済みの利用者は戻さずスキップ**し、件数を報告する（旧リストに載っていても取り消しを覆さない）
- 実際に変わったときだけ、そのアプリの版を1つ進める。同じ入力で再実行しても何も変わらない
- 監査履歴へ `system:migration` として残る。`--dry-run` は何も書かない
- メールは小文字化して取り込む。旧リストが大文字混在で、アプリ側が大文字小文字を区別して比較している場合は、切替前に `diff` で欠落が出ないか確かめる

欠落の内訳（取り消し済み／未登録）が出るので、取り消し済みによる欠落は意図どおりか、未登録による欠落は取り込み漏れかを判断する。

## 復旧

取り込みを誤った場合は、管理画面（監査履歴で変更前後を確認できる）から利用者の付与を直す。管理画面に入れないときは
[access-control.md](./access-control.md) の復旧手順（`scripts/access-recover.mjs`）を使う。
